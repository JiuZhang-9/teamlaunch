# ADR-006: 安全模型：挑战应答 + 写请求签名

## Status

Accepted（2026-09-29）｜ 决策人：高见远 ｜ 影响：发布权限、PRD §14.1 合规

> **2026-09-29 补充（用户已确认，本条不可再推翻）**

> 本 ADR 第 3 节的签名机制不是权宜之计，而是对该条款的合规回应，已由用户本人于 2026-09-29 签字确认。

## Background

PRD §14 非功能需求写明了硬要求：

- "HTTPS/TLS + JWT 短时会话**或经架构师确认的等价机制**"。
- "管理员口令不明文存储或传输"。
- "输入校验、速率限制、发布权限校验；不得自动执行任意脚本"。
- §14.1：连续失败要限速；错误文案不得泄露口令规则或服务细节。

同时产品边界锁死为"设备标识 + 管理员口令，不做账号体系"，运行在纯内网无 PKI 环境。

要防的核心威胁非常具体：**局域网里任何一个人写个脚本往同步服务 POST，就能把全团队的入口墙改掉。**

## Decision

**口令 scrypt 派生存本地 + 挑战应答（口令永不上网）+ 8 小时令牌 + 写请求 HMAC 签名，作为 PRD 允许的等价机制。**

### 1. 口令落地

- 首次以管理员角色运行进入"设置管理员口令"引导，**无默认口令**。
- 最少 8 字符；错误文案不得泄露规则（例如不写"必须包含大写"）。
- `credential.json` 存 `{kdf:'scrypt', N:2**15, r:8, p:1, salt:32B, verifier:32B, createdAt}`，`verifier = scrypt(password, salt, 32)`。明文口令从不落盘。
- 使用 Node 内建 `crypto.scrypt`，不引第三方。
- 写文件后立即用 `icacls` 把 ACL 收敛到当前用户。

##### 1.1 `maxmem` 必须显式指定（2026-09-29 现场修真 bug，不可回退）

**派生时必须显式传 `maxmem: 64 MiB`**，否则 `crypto.scrypt` 直接抛 `ERR_CRYPTO_INVALID_SCRYPT_PARAMS: memory limit exceeded`——表现是"设置管理员口令"这一步当场失败。

原因是一道**只差 1 KiB 的临界账**（已实测，不是估算）：

```
Node 实际校验的用量 = 128·N·r + 128·r·p
                   = 128 × 32768 × 8 + 128 × 8 × 1
                   = 33,555,456 B
Node/OpenSSL 默认 maxmem = 32 MiB = 33,554,432 B
超出                      =            1,024 B
```

正好卡在默认上限之上 1 KiB，所以"看起来 32MB 够用"是错的。

- 常量落在 `src/shared/constants.ts` 的 `AUTH.scrypt`，**两端共用同一份**（服务端校验与客户端解锁必须派生出同一个 verifier）。
- **64 MiB 的覆盖范围是 N ≤ 2^15**：实测 `N=2^16` 配 64 MiB 仍会抛同一错误。因此将来若要提高 N，必须同步抬高 `maxmem`，且因为是共享常量，两端必然同时生效——这是刻意设计的安全性质，不要把它改成运行时可配置项。

##### 1.2 派生参数虽然来自线上，客户端必须先夹紧再派生

`N`/`r`/`p` 由 `/auth/challenge` 下发，客户端**不得**直接把它们喂给 `crypto.scrypt`：

- 收到参数后先与本地 `AUTH.scrypt` 比对，**不一致即拒绝并提示"服务端不受信任"，不要尝试派生**；
- `maxmem` **永不上线**，只取本地常量。

理由：一个被冒充或已失陷的管理员实例只要回一个 `N=2^20`，客户端就会尝试分配 1 GB 内存（`128·N·r`），管理员机器当场卡死——这就是一个不需要任何口令的 DoS。`maxmem` 放进线上字段不但挡不住它（`N` 本身已经是攻击面），还多一个可被伪造的参数，所以维持"只放本地常量 + 夹紧线上参数"的组合。当前 N/r/p 是固定单档，这条是潜伏约束；**一旦有人让 N 变成可配置，这条就是硬要求**。

### 2. 握手：口令永不上网

```
1) POST /api/v1/auth/challenge  {deviceId}
   ← {challengeId, challenge(32B), salt, kdf:{N,r,p}, expiresAt(60s), serverId}

2) 客户端本地：
     verifier = scrypt(password, salt, 32)
     proof    = HMAC-SHA256(key=verifier,
                  msg = challengeId + ":" + challenge + ":" + deviceId + ":" + serverId)

3) POST /api/v1/auth/verify  {challengeId, deviceId, proof}
   服务端用自己存的 verifier 重算，crypto.timingSafeEqual 比对
   ← {token: base64url(randomBytes(32)), expiresAt: now+8h}
```

challenge 单次有效、60 秒过期 ⇒ 同时解决了明文传输与重放。
管理员本地解锁编辑走同一套校验（同一进程内），解锁态仅驻留内存，闲置 10 分钟自动清除（PRD §14.1）。

### 3. 写请求签名：为什么不直接用 Bearer Token

服务是明文 HTTP。若只用 Bearer，局域网被动嗅探者拿到 token 就能在 8 小时内任意发布。因此所有写请求必须签名：

```
Authorization: Bearer <token>
X-TL-Timestamp: <unix ms>
X-TL-Nonce:     <随机串，服务端 5 分钟内去重>
X-TL-Signature: base64(HMAC-SHA256(key=verifier,
    msg = token + "\n" + method + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + sha256(rawBody)))
```

服务端校验顺序：时间戳偏差 ≤ 120 s → nonce 未出现过 → 签名一致，任一失败即 401。

**收益**：攻击者即使嗅探到 token，没有 verifier（即没有口令）也无法构造出任何一次合法发布；同时天然防重放与正文篡改。成本约 80 行中间件，零依赖、无证书维护。

这是本 ADR 对 PRD"等价机制"条款的正式回应，**已于 2026-09-29 由用户确认**（见 Status 补充）。

### 4. 限流与容量

| 项 | 规则 |
|---|---|
| `/auth/verify` | 5 分钟内 > 10 次失败 → 该设备锁定 15 分钟 |
| `/feedback` | 20 条/设备/小时；同 `(entryId, reasonCode)` 24 小时内去重 |
| `/telemetry` | 1 批/设备/分钟 |
| 全局请求体 | ≤ 1 MB（413） |
| 团队配置 | ≤ 8 组 / ≤ 200 入口（422）**在服务端 zod 层强制** |

### 5. 员工能否绕过口令直接改

不能。三层防线：
1. **服务端强制鉴权**（签名中间件）—— UI 隐藏编辑入口只是视觉过滤，不是安全边界。
2. 员工端个人数据永不进入任何请求体。
3. 读取侧 schema + `contentHash` 双重校验，脏数据来源无论身份都被拒。

第 1 条是对"缺失系统上下文"这一失效模式的定向防线，开发必须实现在服务端。

## 安全边界（必须向团队与试点用户明示）

| 能防 | 防不住 |
|---|---|
| 局域网内临时起意的冒名发布 | 对管理员机器有本地文件访问权的人（可删 credential.json 重置口令、可直接改配置） |
| 口令被嗅探（明文从不上网） | 物理占用管理员机器并取得其 Windows 会话的人 |
| 令牌被嗅探后用于发布（缺 verifier 无法签名） | 局域网被动嗅探者**读取**团队入口清单（明文 HTTP） |
| 令牌长期冒用（8 小时过期，仅内存不落盘） | 员工虚构反馈或埋点（靠去重与聚合削弱，不作恶保证） |
| 大数据轰炸（1 MB + 8 组/200 入口硬上限） | 已驻留在管理员机器上的恶意软件（该层防线属于 OS/EDR） |

**口令忘了怎么办**：MVP 不提供找回。删掉 `%APPDATA%\TeamLaunch\credential.json` 后重启客户端即回到首次运行引导重设。这本身就是"本地访问权 = 管理权"的诚实体现，试点说明必须照实写，不能包装成一项安全功能。

## Consequences

**正面**
- 满足 PRD §14.1 全部条款，并以可论证的等价机制替代 TLS（无 PKI 可用性）。
- 零额外依赖、零证书运维 —— 对一个 10–50 人的内网工具，这是恰当的成本点。
- 全部鉴权在服务端，客户端是否诚实不影响安全性。

**负面与代价**
- 明文传输未解决，需在文档中明确列为用户可接受的边界；试点前必须让用户看到这张表。
- `verifier` 在服务端等价于口令（这是这类"服务端派生-校验"方案的固有特性），本地文件因此是最高价值目标，需要 ACL 收敛 + 试点用户教育。
- 签名为自研机制而非标准协议（不像 JOSE/HTTP Message Signatures），将来若做跨组织对接需重评审。

**升级路径（P1）**：自签证书 + 首次连接时公钥固定（TOFU），把第 3 条也纳入防护。届时握手流程不变，只是给 HTTP 套一层 TLS。
