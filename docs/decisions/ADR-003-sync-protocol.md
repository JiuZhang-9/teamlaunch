# ADR-003: 同步协议（版本号、条件请求与软更新）

## Status

Accepted（2026-09-29）｜ 决策人：高见远 ｜ 影响：员工端 UI 更新策略、缓存可靠性、发布一致性

## Background

同步服务是单点（管理员客户端），必须同时满足：

- PRD P0-10：启动拉取、手动刷新、**后台 30 秒比对**。
- PRD AC-08：管理员发布后在线员工 **p95 ≤ 45 秒**内显示新版本，且不能打断当前操作。
- PRD AC-09：版本无变化**不替换卡片列表、不改变焦点、不显示干扰性提示**。
- PRD §13：校验失败保留旧缓存；不得用本机时钟判断版本先后；发布冲突禁止静默覆盖。
- 管理员可能关机、网络可能抖动、多个员工可能同时拉取。

需要定死的三个问题：版本号怎么定、怎么算"有变化"、什么条件下才允许替换缓存。

## Decision

### 1. 版本锚：单调整数 `revision` + 完整性 `contentHash`

| 字段 | 定义 | 不变式 |
|---|---|---|
| `revision` | int64，每次发布 +1 | **永不复用、永不回退**；回滚也产生新的更高 revision |
| `contentHash` | 规范 JSON（键排序、无空白、UTF-8）的 SHA-256 | 用于发现"版本对了但内容坏了" |
| `ETag` | 强校验 `"<revision>-<contentHash前16位>"` | 与 `If-None-Match` 配对 |

- **不用纯内容哈希当版本**：哈希无法比较先后，也无法满足 PRD"生成递增版本"的产品呈现。
- **不用时间戳当版本**：PRD §13 明确要求避免用本机时钟判断先后。因此版本新旧**只比 revision**，时间只用于展示，且展示取服务端 `publishedAt`。

### 2. 条件请求：`If-None-Match` → 304

```
GET /api/v1/config
If-None-Match: "128-9f2c1a7b3d5e0f11"

→ 304 无正文        UI 不做任何重绘（AC-09）
→ 200 + ETag + X-TL-Revision + X-TL-Published-At
```

30 秒轮询在无变化时是零字节传输，这是"轮询不扰民"的技术前提。

### 3. 增量策略：MVP 做"版本闸门式全文档拉取"，不做字段级 diff

**理由**：MVP 上限 200 个入口，正文远小于 500 KB，局域网单次全量 < 30 ms。而字段级 diff 的合并逻辑是"沉默逻辑错误"的高发区——漏合并一个字段会造成两端永久不一致且完全无报错。在一个测试覆盖尚不完备的 MVP 里，全量替换 + 强校验的正确性远高于按字段合并。

真正的增量体现在两处：① `ETag/304` 让无变化零传输；② `GET /api/v1/changes?since=N` 只回变更记录，供发布历史使用。

**升级触发条件**：单次正文 > 2 MB 或入口 > 2000 条时，引入 `/api/v1/config/diff?since=N`。

### 4. 缓存替换的三重闸门（不可省略任一）

只有全部通过才落盘新缓存：

1. HTTP 200；
2. zod Schema 全量校验通过；
3. `sha256(body)` 与响应中的 `contentHash` 一致，且 `revision` 严格大于本地。

任一失败即保留旧缓存并提示"更新未完成，仍使用上一版本"。这条是防止**缓存投毒**的关键防线——包括被代理篡改、被中间件截断、管理员端磁盘半截写入等全部情形。

### 5. 轮询调度

- 间隔 30 s，单次预算 ≤ 15 s ⇒ p95 ≤ 45 s 成立。
- 上一轮未结束时**跳过本轮**，禁止请求堆积。
- 连续 2 次失败 → 下一轮走 ADR-002 的完整发现阶梯，重新绑定端点。
- 仅对幂等 GET 重试（退避 300 ms / 900 ms，最多 2 次）；扫描出的新端点不重试。
- `powerMonitor.on('suspend')` 停表，`'resume'` 与 `'unlock-screen'` 立即触发一次。
- **软更新**：仅当 revision 变化才替换内存快照；渲染层必须保留当前 Tab、滚动位置与搜索词。

### 6. 实际日期：服务端时间，非本机时钟

所有"数据时间"展示取服务端 `X-TL-Published-At` 并随配置缓存落盘。员工机时钟不准不影响版本判定，也不影响跨日显示。

## Consequences

**正面**
- 版本判定与正确性完全不依赖时钟，回应 PRD §13。
- 无变化时轮询是零字节、零重绘，不会打扰（对齐 AC-09 与 PRD 风险"轮询产生视觉跳动、员工被打断"）。
- 缓存永远要么是"上一份完整可用的"，要么是"通过三重校验的新版本"，不存在中间态。
- 服务端回复来自内存快照，天然支持并发拉取，无锁竞争。

**负面与代价**
- 每次有变化都是全文档传输，在规模变大后浪费带宽；已用明确的触发条件（2 MB / 2000 条）守住。
- 单向轮询使"管理员一发布员工立刻看到"不可能实现（最快 1 个轮询周期）。这已被 PRD 接受（≤45 s）。
- 服务端必须维护与磁盘一致的 `currentSnapshot`，多了一处需要保持同步的状态（缓解：发布时同步重算，不引入异步写盘）。
