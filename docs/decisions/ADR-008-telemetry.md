# ADR-008: 遥测方案：本地优先 + 局域网批量上报（零外网出口）

## Status

Accepted（2026-09-29）｜ 决策人：高见远 ｜ 产品确认人：PM ｜ 影响：隐私合规、员工信任、遥测数据安全

## Background

PRD §15.3 把埋点实现选型交给架构："使用轻量 SDK（Mixpanel、Umami 或自建 `trackEvent()` 封装之一），由架构师结合内网与隐私要求选型。"

PRD 同时给出硬约束：
- §14 隐私：不采集 IP、原始搜索词、完整个人路径、个人卡片内容和原始硬件序列号。
- §16.2 隐私合规指标：遥测出站请求出现**第三方外网域名**或服务端日志出现**来源 IP** = **0 条**（一票否决级）。
- §16.3 Go/No-Go：遥测审计通过才可放行。
- §17 风险：遥测默认开启被误读为监控。

PM 已确认产品决策：**默认开启，不做默认关闭；首次启动必须说明并提供关闭开关。**

## Decision

**不接入任何第三方互联网埋点服务。采用自建 `trackEvent()` + 本机缓冲 + 仅向管理员侧局域网端点批量上报。**

### 为什么不用 Mixpanel / Umami

- 这是纯内网团队工具。把员工的使用数据发到公网 SaaS，既违反 §14 的隐私定位，也让产品凭空依赖一个外网服务（离线团队场景下这个依赖还不能保证可用）。
- §16.2 的"第三方外网域名 0 条"指标在用第三方 SDK 时根本无法达成（SDK 会自带域名、带重试、带 CDN）。

### 存储与淘汰

- 本机 `events/events.jsonl` 环形缓冲，**≤5000 条或 14 天，先到者滚动淘汰**。
- `user_id` = `base64url(hmacSha256(installSalt, deviceId)).slice(0,22)`，本地生成、不可逆、非硬件序列号。
- 事件字典对齐 PRD §15.2，不新增字段。

### 三层零外网出口防线（对应 §16.2 指标）

1. **运行时护栏**：发送前校验目标主机，非 RFC1918（`10/8`、`172.16/12`、`192.168/16`）或 link-local（`169.254/16`）**直接丢弃并记本地警告**，不发请求。目标地址只能来自 `discovery/endpoint-resolver.ts`。
2. **CI 静态门禁**：遥测模块内禁止出现字面 `http://` / `https://` 常量，无例外白名单。
3. **依赖白名单**：不引入任何外网 SDK。

### 服务端禁写来源 IP（含访问日志）

- Fastify 自定义日志序列化器显式剔除 `req.remoteAddress` / `req.ip` / `req.socket`。
- 访问日志只输出 `method / path / status / durationMs`。
- 落盘数据只保留客户端上报的 `anonDeviceId`，不补充任何服务端侧来源字段。
- 诊断接口只给设备数量的粗粒度桶，不给明细。

### 首次说明是一道状态门，不是一句文案

新增 `settings.telemetryNoticeAckedAt`：

- **未确认 ⇒ 一律不发送任何上报**，即使默认开启。功能本身完全可用，不受影响。
- 说明必须讲清三件事：上报什么（匿名编号/版本/成功失败次数与原因类别，不含原始搜索词、完整路径、个人入口内容、IP）、为什么（发现打不开的入口和同步状态，不评价个人）、如何关闭（开关位置与关闭影响）。按 PRD §15.3.1 的口径写，不写成法律文本。

### 关闭语义采用更严格的一档

PRD 原话是"关闭后本机不再上报，已缓冲事件不再发送"。本方案进一步做到：
1. 立即停止本地记录新事件；
2. **立即清空本机尚未发送的缓冲事件**；
3. 不再发起任何上报请求。

连本地记录也停掉，比只停上行更隐私正向，也更容易向员工解释清楚。

### 样本残缺与"可判定性"

PRD 已将入口健康指标改为**条件判定**：只有下列两个完整度指标达标，"试点两周后仍被报告失效的入口占比 < 5%"才作为硬判定，否则只做参考 + 逐项人工确认。因此这两个值必须系统可算，不能人工估：

- **事件丢失率 < 20%**：每客户端持久化计数 `events/tel-stats.json`（`recorded / uploaded / droppedByEviction / droppedByRetention`），随每批上报携带；服务端汇总。
- **上报成功设备覆盖 ≥ 70%**：分母取同期成功调用 `/api/v1/config` 的匿名设备数，分子取同期成功调用 `/api/v1/telemetry` 的匿名设备数，均只用 `anonDeviceId` 去重计数，与"不记录来源 IP"无冲突。

两个指标随 `GET /api/v1/diagnostics` 的 `telemetryCompleteness` 只读暴露，并给出 `sampleJudgable` 布尔值。试点当天查一次即可完成 Go/No-Go 的第 4 条判定。

### 样本不可判定时的既定路径（产品已确认，登记以免将来争议）

PM 提出的风险与我方认同的处置路径，同步登记于此：

> 若试点期 `sampleJudgable` 长期为 `false`，说明**遥测在当前管理员在线模式下拿不到足够样本** —— 这不等于入口有问题，也不等于本方案失败。此时应转向 P1 的「管理员内容健康中心 + 逐项人工确认」路径，**而不是改用云端或第三方互联网埋点方案**。

理由：改云端会直接摧毁本 ADR 成立的前提 —— §16.2 的"第三方外网域名 0 条"是一票否决指标，第三方 SDK 自带域名与重试，根本无法达成；同时违反 §14 的隐私边界。

**推翻本条的门槛**：必须同时给出"在不引入外网域名、不记录来源 IP 的前提下如何提升样本量"的方案，并经 PM 与架构师共同评审。仅以"指标拿不到"为由推动上云，不成立。

管理员在线窗口不需要新增机制 —— `team_sync_completed` 的成败序列本身就是证据，试点计划手工记录在线时段即可。

### 防止事件风暴

同一失败不得在轮询循环中重复上报：单一失败 ←→ 单一 `error_occurred`，按 `(errorCategory, operation, failureKey)` 去重。上报失败永不影响入口打开。

## Consequences

**正面**
- 天然满足 §16.2 与 §16.3 的隐私一票否决项，且是**可被机器验证**的（抓包 + 日志审计）。
- 无外网依赖，离线团队场景下可用性更好。
- 关闭语义比 PRD 要求更严，降低 R19"被误读为监控"的概率。

**负面与代价**
- 管理员离线时数据滞后：健康数据只能在管理员在线时被收集；管理员长期离线会丢一部分样本 —— 可通过本地缓冲 14 天缓解，但不可能像云端那样完整。**这是本方案最主要的缺点，也是 PRD 把入口健康改为"条件判定指标"的直接原因**；本 ADR 通过 §"样本残缺与可判定性"提供可判定的门槛，避免用残缺样本得出错误结论。
- 放弃了对使用漏斗做长期趋势分析的能力（样本随缓冲滚动淘汰而丢失）。
- 自建意味着要自己维护事件字典与脱敏校验，这部分工作量转移到了团队内部。
