# TeamLaunch（团队启动器）MVP 产品需求文档

- 文档版本：0.1
- 日期：2026-09-29
- 产品阶段：MVP
- 目标平台：Windows 桌面端
- 预设团队规模：10–50 人内网团队
- 决策状态：本文继承项目已锁定决策；未在本文中重新讨论客户端形态、同步服务落点、编辑入口与身份方案。

## 0. 执行摘要

### 一句话描述

TeamLaunch 是面向 10–50 人内网团队的 Windows 统一入口：管理员把团队常用软件、文件夹和网页发布为一张可搜索的卡片墙，员工一处打开；个人入口留在本机，网络或管理员设备不可用时仍可使用最近成功缓存。

### 真正要解决的问题

用户表面上要“把快捷方式放在一起”，真实问题是：团队入口散落在桌面、开始菜单、浏览器书签、群公告和共享盘中，成员不知道“该去哪里找、哪个才是最新版、打不开该找谁”，管理员也缺少一次发布、全员收敛、失效可反馈的轻量机制。

### MVP 的三个核心能力

1. **统一入口工作区**：团队页与个人页、三类入口、一键打开、分组卡片墙、搜索与 Windows 快速唤起。
2. **团队内容发布闭环**：管理员可视化编辑并发布，员工启动、手动刷新与后台轮询获取新版本；失败时回退本机缓存。
3. **失效诊断与反馈闭环**：本机缺软件、路径不存在或系统拒绝打开时给出可执行解释；员工可结构化反馈给管理员。

### 五个关键产品结论

1. **信息组织采用“单层分组 + 组内卡片平铺”**。仅允许一层分组，不做分组嵌套；建议团队页不超过 8 组，超出时提示合并。
2. **三类入口使用相同卡片骨架，以“类型 SVG 图标 + 类型文字标签 + 次要元信息”区分**。不能只靠颜色；软件可优先显示程序自带图标，失败时回退统一的软件类型 SVG 图标。
3. **需要“反馈给管理员”**。自动提示只覆盖本机可判断的错误；网页在浏览器中打开后仍失败时，由员工主动报告。反馈预填入口、错误类型和时间，允许补一句说明，不做聊天系统。
4. **发布后在线员工端软更新，不强制整窗刷新，也不等下次启动**。30 秒轮询版本号，发现新版本后更新团队数据并显示轻提示；无变化不重绘，当前点击不被打断。
5. **团队页与个人页采用并列主 Tab**。团队页排第一并作为首次启动默认页；不采用上下混排，也不为两个页面引入过重的侧边栏。

## 1. 行业知识库基线

本 PRD 在联网调研前参考了一份本地行业知识库（企业管理 / ERP 行业设计规范，内部资料，不随本仓库分发）。

采用的行业基线：

- 企业工具应专业稳健、信息密度适中、操作路径短。
- 与本产品最接近的是“工作台模式”：卡片网格与快捷入口。
- 权限状态必须直观，普通员工不能误以为自己可编辑团队内容。
- 状态反馈应明确，尤其是离线、草稿、已发布、失败和权限拒绝。
- 视觉不追求花哨，每屏强调色控制在少数关键动作上。

本项目补充约束：

- 功能图标统一使用 SVG 图标库，具体库由架构师结合项目锁定；禁止使用 emoji 作为功能图标。
- 主视觉禁止紫色到粉色渐变。
- 示例文案必须来自真实团队场景，不使用空洞占位文案。

## 2. 产品定义

### 2.1 目标用户

- 主要用户：10–50 人团队中的普通员工，日常需要反复打开固定软件、项目目录、共享盘位置和内部网页。
- 主要管理用户：行政、IT 兼职管理员、项目运营或团队负责人，需要维护“全员应看到的入口”，但不希望改配置文件或维护独立服务器。
- 次要用户：新入职员工、短期协作成员，以及需要维护个人快捷入口的高频办公用户。

### 2.2 核心问题

| 角色 | 场景 | 当前痛点 | 现有办法为什么不够 |
|---|---|---|---|
| 普通员工 | 每天开始工作、切换项目 | 入口散落，记不住软件名、路径或网址 | 开始菜单只适合本机应用；书签只管网页；共享盘快捷方式缺少清晰说明 |
| 新员工 | 入职第一周 | 不知道团队标准工具和最新入口 | 靠同事逐条发送，信息易过期且缺上下文 |
| 管理员 | 地址、目录或工具更新 | 需要逐群通知，无法确认成员何时拿到新版 | 群公告会沉没；脚本对非技术管理员不友好；独立服务运维过重 |
| 员工与管理员 | 管理员设备不在线 | 担心所有入口不可用 | 纯在线工作台会阻断使用；共享配置又缺版本与状态说明 |
| 员工 | 卡片打不开 | 不知道是本机没安装、路径失效还是链接问题 | 截图发群缺少结构化上下文，管理员难以聚合定位 |

### 2.3 产品目标

1. 把团队常用的三类入口收敛到一个两步内可达的工作区。
2. 让非技术管理员在客户端内完成新增、整理、校验、发布和查看最近变更。
3. 在线时让团队页在发布后尽快一致，离线时不阻断已缓存入口。
4. 让失效入口形成“可解释、可反馈、可修复”的闭环。
5. 保留个人自由整理空间，但不把个人内容回传或混入团队真理源。

### 2.4 非目标

TeamLaunch 不是通用搜索引擎、应用商店、软件分发系统、企业协同套件、流程自动化平台，也不是员工行为监控工具。

## 3. 用户画像

### 画像 A：林岚，团队入口管理员

- 年龄与职业：32 岁，创业团队行政兼 IT 支持。
- 技术水平：能安装软件和处理基础网络问题，不写脚本。
- 典型环境：维护 28 台 Windows 电脑；常用工具包括客服软件、共享项目目录、报销网页和会议链接。
- 核心任务：把入口改一次，全员看到同一版本；能看出哪些设备报告了哪个入口有问题。
- 最大焦虑：自己电脑关机时不能让团队“什么都打不开”；也不想维护 NAS 或独立服务器。
- 成功定义：10 分钟内完成一次内容调整和发布，不必逐个群通知。

### 画像 B：周鸣，一线员工

- 年龄与职业：26 岁，运营专员。
- 技术水平：熟悉浏览器和 Office，不熟悉路径、命令和网络配置。
- 典型环境：每天打开 8–12 个固定入口，主要靠桌面图标、收藏夹和同事发来的消息。
- 核心任务：知道从哪里打开正确入口，并在打不开时获得明确下一步。
- 最大焦虑：搜索到同名旧链接、共享盘路径变化、换电脑后桌面快捷方式全丢。
- 成功定义：看到卡片名称就能判断用途，点击后立即打开；失败时不需要描述复杂错误。

### 画像 C：赵新，新入职员工

- 年龄与职业：23 岁，新入职设计助理。
- 技术水平：日常办公熟练，但不了解公司目录结构与工具约定。
- 典型环境：首日需要安装并找到十余个入口，管理员同时还在处理其他入职事项。
- 核心任务：快速认识团队标准工具，区分“公司统一入口”和“我自己的入口”。
- 最大焦虑：拿到一堆链接却不知道用途，或者本机缺软件却误以为入口失效。
- 成功定义：首次打开 30 秒内找到指定入口；遇到未安装软件时能直接报告准确原因。

## 4. 用户故事与核心场景

### 场景 1：晨间启动

周鸣开机后 TeamLaunch 随系统启动并驻留托盘。他点击“团队入口”中的“客服工作台”，随后打开“本周活动素材”文件夹。两个入口来自同一工作区，不再分别翻开始菜单和资源管理器。

**用户故事**：作为普通员工，我希望在同一个界面看到团队标准入口，以便在不记路径和网址的情况下开始工作。

### 场景 2：管理员变更共享目录

林岚进入管理员编辑模式，把“旧版报价模板”替换成“2026 秋季报价模板”，系统显示变更预览“新增 1 项、修改 1 项、删除 0 项”。她补充说明“报价目录迁移”，确认发布。在线员工在下一次 30 秒轮询内拿到新版本，当前窗口不整页闪烁。

**用户故事**：作为管理员，我希望一次发布后在线成员自动拿到最新版，以免重复通知并减少旧入口继续流通。

### 场景 3：管理员设备离线

下午管理员笔记本关机。赵新打开 TeamLaunch，应用继续展示上午 10:42 成功同步的团队页，顶部显示“离线，数据时间 10:42”。已缓存的本地软件和文件夹入口仍可点击；手动刷新失败不会清空页面。

**用户故事**：作为员工，我希望同步端不可用时仍能使用最后一次成功内容，以免管理员是否在岗决定我能否工作。

### 场景 4：入口在本机失效

赵新点击“设计审稿工具”，本机未找到对应程序。界面显示“本机未找到该软件”，提供“重新定位”和“反馈给管理员”。他选择原因“本机未安装”并提交。管理员收到按入口聚合的反馈，而不是一张缺少上下文的截图。

**用户故事**：作为员工，我希望打不开时知道原因并一键反馈，以便管理员快速判断是个别电脑问题还是团队配置问题。

### 场景 5：个人入口不污染团队页

周鸣在“我的入口”新增自己的“月报草稿”文件夹。该入口仅在本机可见。他更换电脑前导出个人入口 JSON，在新电脑导入；团队页不受影响。

**用户故事**：作为员工，我希望保留个人快捷入口，但不把私人目录同步给团队或要求管理员维护。

## 5. 信息架构与关键交互结论

### 5.1 团队页的信息组织

**结论：单层分组与卡片平铺结合。**

- 页面顶层只有“团队入口”“我的入口”两个并列主 Tab。
- 团队页内按业务语义建立一层分组，例如“日常办公”“项目资料”“运营系统”。
- 每组内使用统一卡片网格；管理员可调整分组顺序与卡片顺序。
- 不允许分组套分组，避免员工为一个入口连续展开多层。
- 建议上限为 8 个团队分组、每组 24 张卡片、团队页总计 200 张卡片。达到建议上限时给出整理提示，不静默截断。
- 未分组入口进入“其他”组；空组不在员工端展示。
- 搜索跨所有分组，并在结果中保留“团队/个人”“所属分组”和入口类型。

选择理由：纯平铺在入口超过约 20 个后定位成本上升；多层目录又会复制文件系统的迷路问题。一层分组保留扫视效率，也让管理员能表达团队语义。

### 5.2 三类入口的视觉区分

三类入口共用相同尺寸、标题层级、状态区和点击行为，差异仅用于快速识别：

| 类型 | 主识别 | 次要信息 | 失败状态文案示例 |
|---|---|---|---|
| 软件 | 程序自带图标；不可取时用统一“应用程序”SVG 图标 | “软件”文字标签，可显示程序名称 | “本机未找到该软件” |
| 文件夹 | 统一“文件夹”SVG 图标 | “文件夹”文字标签，可显示路径末级名称 | “文件夹不存在或当前无权限” |
| 网页 | 网站图标；不可取时用统一“网页链接”SVG 图标 | “网页”文字标签，可显示域名 | “链接格式无效”或由用户主动报告“网页打不开” |

要求：

- 不能只靠颜色区分，必须同时有 SVG 图标与文字标签。
- 卡片标题最多两行，完整名称和完整路径在详情或悬浮提示中查看。
- 卡片不显示无解释的技术错误码；“查看详情”中可复制诊断信息。
- 不使用 emoji 作为类型、状态或操作图标。

### 5.3 失效入口处理

**结论：要做“反馈给管理员”，但不做即时聊天。**

1. 点击前可本机判断的错误直接解释：程序或路径不存在、权限拒绝、格式非法。
2. 对网页只保证成功交给默认浏览器；浏览器内的 404、登录失败或业务报错由员工主动选择“反馈失效”。
3. 反馈预填入口 ID、当前发布版本、入口类型、失败原因、发生时间和匿名安装标识；员工可补充不超过 200 字说明。
4. 离线时保存为“待发送”，重新连上管理员同步服务后自动重试；员工可取消未发送反馈。
5. 管理员看到按入口聚合的待处理反馈数量、原因分布与最近时间；不展示员工原始硬件序列号。
6. 同一设备对同一入口的重复反馈合并，防止误触刷屏。

### 5.4 发布后的刷新策略

**结论：软更新，在线快速生效，不整窗强刷。**

- 启动时拉取一次。
- 员工可从页面和托盘手动刷新。
- 后台每 30 秒仅比对版本号；版本无变化时不重绘。
- 发现新版本后拉取并替换团队数据，保留当前 Tab、搜索词和滚动位置；若目标卡片已被删除，关闭其详情并提示“该入口已由管理员移除”。
- 当前正在打开外部资源的动作不被中断。
- 更新成功显示短暂的“团队入口已更新至 vX”状态，不要求用户确认。
- 发布目标：管理员发布后，在线员工 p95 在 45 秒内看到新版本。
- **在线状态不得沿用上一轮结果（产品硬规则）**：同步状态必须由本轮轮询结果决定，禁止 UI 依据“本地版本没变”自行推导在线状态。
  - “已是最新”状态的有效期只到下一轮轮询结束为止；下一轮未成功完成时必须退回离线/未知，不允许继续显示“已是最新”。
  - 管理员服务不可达时，员工端必须显示离线与数据时间，或明确显示“未找到同步服务”，不得沿用旧状态。
  - 失败反馈仍可离线排队，但界面不得暗示“已上报成功”。

### 5.4.1 同步状态机要求（与架构 T3.6 对齐）

- 必须定义显式同步状态集合，禁止用布尔“在线/离线”表达。**六类语义必须都可观察**：首次未同步、正在同步、在线且已最新、在线但有更新待应用、离线且有缓存、离线且无缓存、同步失败/未知。
- 允许的落地形态（架构 v1.2）：`NEVER_SYNCED` / `SYNCING` / `ONLINE_LATEST` / `ONLINE_UPDATE_PENDING` / `OFFLINE_CACHED` / `OFFLINE_EMPTY` / `SYNC_FAILED_UNKNOWN`。
- 故障原因与缓存有无是两个正交维度，采用“状态 + 原因”表达，不把原因扁平进状态枚举：
  - `offlineReason`：决定“未找到同步服务”还是“被拦截/不可达”的文案，由同步服务写入；
  - `hasCache`：决定离线时展示缓存还是空状态。
- 状态与伴随字段只能由同步服务写入；页面不得自行推导或缓存上一轮状态；UI 禁止用“卡片数为 0”推断 `hasCache`。
- 状态变化要有可观察提示；无变化时不重绘、不闪烁。
- **离线空态必须区分“管理员没发内容”与“拿不到数据”**：有成功缓存但缓存内容为空时显示正常空态（“团队入口还没有内容”），不得显示为离线或故障；只有从未成功同步/无缓存时才走离线空态。

### 5.4.1.1 离线文案口径（产品裁定）

- 离线/失败状态的**主标题一律使用状态语义**：“暂时无法获取团队入口”。不使用“未找到同步服务”作为面向员工的主标题。
- 具体故障原因放在**第二行**，由 `offlineReason` 决定，例如：“管理员电脑未开机或未连接网络”“连接被安全软件或网络策略拦截”“返回数据校验失败，仍使用上一版本”。
- 未覆盖的原因码一律回退到兜底原因行，**禁止显示原始错误码、堆栈或端口/地址**；技术细节只允许出现在可复制的“查看诊断”文本中。
- 第二行必须给出下一步动作（稍后自动重试 / 手动刷新 / 使用我的入口）。

### 5.4.2 失效反馈的投递状态（与架构 T3.7 对齐）

- 反馈投递采用三态：`PENDING`（待发送） / `SENT`（已送达） / `DROPPED`（已丢弃且需告知）。
- 只有服务端确认接收成功才允许转为 `SENT`；**写入本地待发队列不算成功**，`circle-check` 一类成功图标不得用于 `PENDING`，界面不得显示“已上报成功”。
- `PENDING` 文案不得假设失败原因：使用“反馈已保存，稍后自动发送”，不得写成“联网后自动发送”（失败原因可能是管理员电脑不可达，而非本机断网）。
- `DROPPED`（超出队列上限或保留期限）必须可见告知，不允许静默丢弃，也不允许只写日志；告知必须包含具体原因（不显示错误码）与“重新提交”动作，重新提交后回到 `PENDING` 且视觉立即切回待发送态。
- `DROPPED` 的提示为常驻提示，直到用户处理；不得用会自动消失的轻提示呈现坏消息。
- 埋点 `delivery_state` 与上述三态保持同一口径。

### 5.5 团队页与个人页视觉权重

**结论：并列 Tab，团队优先而非团队独占。**

- “团队入口”排在左侧并作为新安装首次启动默认页；“我的入口”与其同级。
- 团队卡片带“团队”来源文字，个人卡片带“个人”来源文字；来源不能只靠颜色。
- 不采用上下分区：会压缩卡片空间并让两套内容混在一次滚动中。
- 不采用侧边栏作为 MVP 主导航：当前只有两个一级页面，侧边栏增加视觉重量却不增加信息价值。
- 全局搜索可同时返回两类结果；同等匹配度下团队入口在前，但始终显示来源。

### 6.3 差评洞察与市场空白

1. **功能越多不等于入口越快**：uTools、Flow Launcher 和协同套件的共同风险是配置、插件或层级膨胀。市场空白是“只做团队常用入口，默认即用”。
2. **键盘优先会排除一部分普通员工**：优秀启动器往往服务高阶用户；10–50 人团队里仍有大量鼠标优先用户，因此需要可扫视的卡片墙，同时保留热键搜索。
3. **个人效率工具缺少团队治理**：Listary、Flow Launcher、Fences 擅长个人整理，但没有“管理员一次发布、员工只读、版本一致”的轻量闭环。
4. **大型协同套件太重且偏网页应用**：企业微信和飞书可以承载应用门户，但本地 exe、共享文件夹与离线缓存不是其核心路径。
5. **扩展生态带来稳定性债务**：插件越开放，质量越难统一。MVP 不做插件市场和任意脚本执行，优先保证三类入口稳定。
6. **离线不是异常边角，而是架构前提转化出的产品需求**：管理员客户端既是同步服务，就必然存在不在线时段；缓存时间必须可见，且失败不能清空可用数据。
7. **“打不开”必须分清团队配置错误与本机差异**：同一个软件路径无法假设全员一致，缺安装、盘符不同、共享盘权限和网页业务错误需要不同反馈。

说明：社区帖子、应用商店评论和 GitHub issue 用于发现问题类型，不代表问题发生率；定价与功能以官方页面为高优先级依据。

## 7. 我们的差异化

### 定位

不是再做一个更全能的个人启动器，而是做“团队入口发布器”：让非技术管理员维护团队真理源，让员工在有网和无网时都能快速打开，并把失效情况结构化反馈回来。

### 为什么用户选择 TeamLaunch

- 比开始菜单和书签更完整：同时容纳软件、文件夹、网页。
- 比共享快捷方式更清晰：卡片有名称、说明、分组、类型、版本和状态。
- 比个人启动器更可治理：团队页由管理员单向发布，员工不会产生分叉配置。
- 比企业协同工作台更轻：不要求账号体系，不承载聊天、审批和文档编辑。
- 比纯在线门户更可靠：管理员离线时仍用最近缓存，不阻断核心打开动作。
- 比群里报错更可处理：失效反馈自动带入口与版本上下文。

## 8. 功能优先级与 RICE

### 8.1 评分口径

`RICE Score = (Reach × Impact × Confidence) / Effort`

- Reach：1–10，按一个季度内覆盖目标团队用户比例估算。
- Impact：0.25 / 0.5 / 1 / 2 / 3。
- Confidence：50% / 80% / 100%。
- Effort：1–10，为相对人月投入档位，不代表技术排期承诺。
- RICE 用于比较价值；已锁定的基础能力即便有依赖，也不能被低成本增强项替代。

### 8.2 Epic 级 RICE 排序

## 9. MVP 范围

MVP 仅保留 RICE 排名前三的 Epic：

1. 统一入口工作区。
2. 团队内容发布与离线同步。
3. 失效诊断与反馈闭环。

P0-01 至 P0-12 是三个 Epic 的必要子能力，不视为 12 个独立产品方向。P1/P2 全部进入 Backlog，不得为了“看起来功能丰富”进入首版。

### MVP 端到端最小闭环

管理员解锁编辑模式，创建一层分组并添加软件、文件夹、网页，发布生成新版本；在线员工在 45 秒内获得更新，离线员工继续使用缓存；员工可从团队页或热键搜索打开入口，失败时获得解释并反馈；个人入口可本机维护和导入导出。

## 10. 明确不做的功能

| 不做项 | MVP 不做原因 | 何时再考虑 |
|---|---|---|
| 账号注册、手机号、邮箱、SSO | 与轻量身份方案冲突，增加部署和隐私成本 | 跨网络、跨组织或需要人员级审计时 |

| 任意脚本、插件市场、自定义命令 | 引入执行安全和兼容性风险，也会复制插件生态的质量问题 | 三类入口稳定、出现高频可复用工作流且有审核机制时 |
| 团队聊天、公告、审批、文档编辑 | 已有企业微信/飞书等工具，本产品不替代协同套件 | 不考虑；仅允许链接跳转到现有系统 |
| 员工使用排行榜或个人行为监控 | 违背轻量入口定位并带来信任风险 | 不以个人绩效用途考虑；只保留匿名产品健康指标 |
| 一键回滚历史版本 | 首版优先保证发布、记录和缓存可靠；回滚需要额外的冲突与数据保护规则 | 发布错误发生率超过 2%，且手工修复影响明显时 |
| 互联网远程访问管理员同步服务 | 扩大攻击面并改变内网产品边界 | 明确出现跨地点办公需求并完成安全评审时 |

## 11. 详细产品规则

### 11.1 入口字段

每个团队入口至少包含：

- 唯一入口 ID。
- 名称：必填，建议 1–40 个字符。
- 类型：软件、文件夹或网页，三选一。
- 目标：程序/快捷方式位置、文件夹位置或 URL。
- 所属分组：一层。
- 说明：可选，建议不超过 80 字，说明“用来做什么”而不是重复标题。
- 搜索关键词：可选，不向员工展示为主文案。
- 图标：程序图标、网站图标或统一 SVG 回退图标。
- 排序值与发布版本。

个人入口使用相同的可见字段，但不进入团队发布版本，也不出现在管理员发布历史。

### 11.2 团队编辑与发布规则

- 普通模式中不显示可误触的编辑把手；管理员解锁后出现清晰的“编辑模式”状态。
- 编辑产生本机草稿，未发布前员工端不可见。
- 发布前校验：名称非空、类型与目标匹配、URL 格式合法、重复目标提示、空分组提示。
- 本机路径可校验只代表管理员电脑上的状态；不得把“管理员本机存在”表达成“全员一定可用”。
- 系统自动生成变更摘要，如“新增 2 项、修改 1 项、删除 0 项”；管理员可补充真实说明。
- 发布成功后生成递增版本并记录时间与摘要，保留最近 20 条。
- 发布过程中若发现团队真理源版本已改变，阻止静默覆盖并要求管理员先查看最新版本。

### 11.3 个人入口规则

- 员工可自由新增、编辑、删除和排序个人入口。
- 个人数据不进入团队同步、管理员视图或团队埋点明细。
- 导出 JSON 前显示包含的入口数量与保存位置；导入前预览新增、覆盖、冲突数量。
- 同 ID 冲突默认不静默覆盖：用户选择跳过、覆盖或另存为副本。
- 非法或损坏 JSON 不改变现有个人数据，并给出可复制的错误说明。

### 11.4 同步与离线规则

- 团队页单向同步，管理员发布版本是真理源；员工永不回写团队配置。
- 每次成功获取并验证完整团队数据后才替换本机缓存，失败不得覆盖上一份可用缓存。
- 在线状态显示最近同步时间；离线状态显示“离线，数据时间 HH:mm”，跨日时显示日期与时间。
- 离线不阻塞本地软件和本地文件夹打开；网页能否打开由实际网络决定。
- 首次使用且没有缓存、管理员又不可达时，展示空状态：“暂时无法获取团队入口。你仍可使用我的入口，并可稍后刷新。”

### 11.5 热键与托盘规则

- 默认全局热键 Ctrl+Space，首次检测到冲突时提示用户修改，不抢占已有关键工作流。
- 搜索面板可用键盘上下选择、Enter 打开、Esc 关闭，也可使用鼠标。
- 托盘菜单固定为“打开”“刷新”“退出”；“刷新”完成后给出成功、无变化或离线结果。
- 开机自启和托盘常驻均可关闭；关闭托盘常驻时退出窗口的含义必须明确，避免应用看似关闭却仍运行。

## 12. 验收标准（Given / When / Then）

### AC-01 团队与个人分层

- Given 用户处于普通员工模式，When 打开主窗口，Then 顶部显示“团队入口”“我的入口”两个并列 Tab，首次默认团队入口，团队内容无编辑控件。

### AC-02 三类入口打开

- Given 卡片目标在本机有效，When 用户单击软件、文件夹或网页卡片，Then 系统使用对应默认方式打开，主窗口保持可继续操作。

### AC-03 类型可识别

- Given 三种入口名称相似，When 用户查看卡片或搜索结果，Then 每项均同时显示类型 SVG 图标与类型文字，关闭颜色辨识后仍可区分。

### AC-04 搜索与热键

- Given 应用在后台运行且热键无冲突，When 用户按 Ctrl+Space 并输入名称、关键词、分组或域名/路径末级，Then 300 毫秒内出现首批本地结果，Enter 可打开所选项。

### AC-05 热键冲突

- Given Ctrl+Space 已被其他应用占用，When TeamLaunch 首次注册热键失败，Then 告知冲突并引导设置替代热键，不反复弹窗或静默抢占。

### AC-06 管理员编辑与发布

- Given 设备标识有效且管理员口令验证通过，When 管理员编辑内容并确认发布，Then 先显示校验结果与变更摘要，成功后生成更高版本并新增一条发布记录。

### AC-07 发布校验失败

- Given 存在空名称、非法 URL 或缺失目标，When 管理员点击发布，Then 阻止发布，定位到问题项，并保留其他未发布编辑。

### AC-08 在线同步

- Given 员工端在线且正在显示旧版本，When 管理员发布新版本，Then 员工端通过 30 秒轮询发现变化并在 p95 45 秒内软更新；明确接受“最快一个轮询周期”的时效口径，不做实时推送，但界面不得把已发布内容表达成“已是最新”之外的误导状态。

### AC-09 无变化不重绘

- Given 员工端版本与管理员版本一致，When 后台轮询完成，Then 不替换卡片列表、不改变焦点、不显示干扰性提示。

### AC-10 离线缓存

- Given 设备至少成功同步过一次，When 管理员设备不可达且用户启动应用，Then 3 秒内展示最近成功缓存，顶部显示离线状态与缓存时间，卡片仍可点击。

### AC-11 首次离线

- Given 设备从未成功同步且管理员设备不可达，When 用户打开团队入口，Then 显示可理解的空状态、手动刷新按钮和“我的入口”入口，不显示空白页。

### AC-12 本机缺软件或路径

- Given 软件或文件夹目标在本机不存在，When 用户点击卡片，Then 不崩溃、不无限加载，显示“本机未找到该软件”或“文件夹不存在或当前无权限”，并提供重新定位、复制诊断和反馈入口。

### AC-13 失效反馈

- Given 员工选择“反馈给管理员”，When 选定原因并提交，Then 在线且服务端确认接收后显示“已送达”；离线或尚未确认时显示“待发送”，并在恢复连接后自动重试；界面不得在待发送状态下显示“已上报成功”。

### AC-13a 反馈超限丢弃

- Given 待发送反馈超出队列上限或保留期限，When 系统丢弃该反馈，Then 必须向用户可见告知丢弃原因与可重新提交的入口，不允许静默丢弃。

### AC-14 个人入口隔离

- Given 员工在“我的入口”新增一个本地文件夹，When 管理员发布或其他员工刷新，Then 该个人入口不出现在团队数据、管理员编辑列表或其他设备上。

### AC-15 个人导入失败保护

- Given 用户选择损坏或不受支持的 JSON，When 执行导入，Then 现有个人入口保持不变，界面说明失败原因并允许复制诊断。

### AC-16 发布历史

- Given 已累计 21 次发布，When 管理员查看发布历史，Then 仅保留最近 20 条，每条包含时间、版本和变更摘要，顺序从新到旧。

### AC-17 开始菜单扫描

- Given 管理员或个人用户发起扫描，When 扫描完成，Then 结果作为候选列表供勾选，不自动把所有程序加入卡片墙；重复目标给出提示。

### AC-18 托盘菜单

- Given 应用驻留托盘，When 用户打开托盘菜单，Then 仅显示并可执行“打开”“刷新”“退出”，刷新结果可感知，退出后应用和同步服务按角色正确停止。

## 13. 边界条件与状态设计

| 类别 | 边界条件 | 产品行为 |
|---|---|---|
| 空状态 | 团队版已获取但管理员尚未发布入口 | 显示“团队入口尚未配置”，员工无编辑按钮；管理员有“添加第一个入口”动作 |
| 首次离线 | 无缓存且管理员不可达 | 不伪造示例卡片；说明现状并提供刷新和个人页 |
| 已缓存离线 | 有旧缓存 | 使用缓存，持续显示数据时间；手动刷新失败不清空 |
| 加载 | 首次同步超过 300 毫秒 | 显示稳定骨架或进度文案，不能让卡片反复跳动 |
| 数据损坏 | 新版本校验失败 | 保留旧缓存，显示“更新未完成，仍使用上一版本”，允许复制诊断 |
| 软件缺失 | exe/快捷方式目标不存在 | 清楚说明是本机问题的可能性，提供重新定位和反馈 |
| 文件夹不可达 | 本地目录、映射盘或共享路径不可达 | 区分“不存在/网络位置不可达/无权限”能识别的结果；不直接删除卡片 |
| 网页失败 | URL 格式非法或无法交给浏览器 | 格式非法由系统阻止；浏览器内业务错误由用户主动反馈 |
| 权限拒绝 | 打开目标需更高系统权限 | 不自动提权；说明“当前无权限”，由管理员或 IT 处理 |
| 重复点击 | 用户连续快速点击同一卡片 | 短时间内合并重复打开请求，避免启动多个相同窗口；仍提供再次主动打开方式 |
| 发布冲突 | 编辑期间真理源版本改变 | 禁止静默覆盖，要求刷新并重新确认差异 |
| 导入冲突 | 个人 JSON 中 ID 或目标重复 | 预览并让用户选择跳过、覆盖或另存副本 |
| 容量边界 | 超过 8 组或 200 个团队入口 | 管理员侧发布前提示信息架构过载；服务端强制拦截超出上限的发布请求，不依赖客户端提示 |
| 权限边界 | 员工端 UI 隐藏团队编辑入口 | UI 隐藏只是视觉层，发布权限必须在服务端校验；绕过客户端直接调用接口也必须被拒绝 |
| 系统提权 | 打开目标需要更高系统权限 | MVP 明确不做自动提权（`runAsAdmin` 出范围）；显示“当前无权限”，提供复制诊断和反馈入口 |
| 长文本 | 名称、说明、路径超出卡片宽度 | 卡片截断但详情显示完整值；不能撑坏网格 |
| 热键冲突 | Ctrl+Space 被输入法或其他工具占用 | 提示修改；鼠标与托盘入口始终可用 |
| 服务退出 | 管理员从托盘退出 | 告知同步服务将停止、员工将使用缓存；避免无感停止 |
| 反馈洪峰 | 多台设备报告同一入口 | 管理员侧按入口聚合，展示设备数和最近时间，而非重复消息轰炸 |
| 时钟不准 | 员工设备时间异常 | 版本先后只比较服务端 revision，绝不使用本机时钟；界面“数据时间”取服务端发布时间 |

## 15. 数据埋点方案

### 15.1 原则

- 事件命名采用 `{对象}_{动作}`；保留项目要求中的通用漏斗事件名。
- 每个事件包含 `user_id`、`timestamp`、`device`、`version`。其中 `user_id` 是本地生成的匿名安装 ID，不是账号、手机号或原始硬件序列号。
- 不上报 IP，不记录原始搜索词、完整路径、URL 查询参数、员工补充说明正文或个人入口内容。
- 个人页只记录聚合动作类型与成功/失败，不记录目标值。
- 员工可以看到隐私说明；管理员只能看到聚合产品健康数据与处理失效反馈所必需的信息。

### 15.2 MVP 必埋事件

| 事件类别 | 必埋事件 | 触发时机 | 关键属性 |
|---|---|---|---|
| 获客/初始化 | `page_view` | 打开团队页或个人页 | `page_type`, `source` |
| 获客/初始化 | `sign_up_complete` | 无账号场景下用于兼容通用漏斗：设备首次初始化完成 | `signup_mode=device_activation` |
| 激活 | `first_core_action` | 首次成功打开任一入口 | `entry_type`, `entry_source` |
| 核心行为 | `entry_open_attempted` | 点击或搜索执行入口 | `entry_type`, `entry_source`, `team_entry_id`, `launch_source` |
| 核心行为 | `entry_open_dispatched` | 成功交给操作系统或默认浏览器 | `entry_type`, `latency_bucket` |
| 异常 | `entry_open_failed` | 本机可判断的打开失败 | `entry_type`, `reason_code`, `team_entry_id` |
| 同步 | `team_sync_completed` | 启动、手动或轮询同步结束 | `trigger`, `result`, `from_version`, `to_version`, `latency_bucket` |
| 离线 | `offline_cache_rendered` | 使用本机缓存展示团队页 | `cache_age_bucket`, `reason_code` |
| 反馈 | `entry_feedback_submitted` | 反馈在线发送或进入待发送 | `reason_code`, `delivery_state`, `team_entry_id` |
| 发布 | `team_publish_completed` | 管理员成功发布 | `from_version`, `to_version`, `added_count`, `updated_count`, `deleted_count` |
| 留存 | `session_start` | 每次有效会话开始 | `start_source`, `network_state` |
| 留存 | `session_duration` | 会话结束或周期汇总 | `duration_bucket`, `active_action_count` |
| 转化 | `upgrade_click` | MVP 无付费入口，不产生事件；保留命名规范 | `not_applicable_reason=no_paid_plan` |
| 转化 | `payment_complete` | MVP 无支付流程，不产生事件；保留命名规范 | `not_applicable_reason=no_paid_plan` |
| 异常 | `error_occurred` | 前端未处理错误或同步 API 错误 | `error_category`, `operation`, `version`, `recoverable` |

### 15.3 实现要求

- **不接入 Mixpanel、Umami 等第三方互联网埋点服务**。采用自建 `trackEvent()` 封装 + 本机事件文件缓冲，仅在用户未关闭时批量上报到管理员客户端的团队遥测接口。
- 本机缓冲上限：5000 条或 14 天，先到者触发滚动淘汰。
- 脱敏要求：`user_id` 为本地生成的匿名安装 ID（不可逆 HMAC），不得使用账号、手机号或原始硬件序列号；服务端不得记录来源 IP，访问日志也不记录。
- **默认上报策略（产品决策）**：默认开启，但首次启动必须有一次可理解的说明，且在“设置”中提供关闭开关。管理员不得查看单个设备的行为序列，只能查看聚合健康数据。
- **关闭遥测后的行为（采用更严一档，产品确认）**：关闭开关后必须同时做到三点，不允许只停上行、继续本地记录：
  1. 立即停止记录新的本地事件；
  2. 立即清空尚未发送的本地缓冲；
  3. 不再向任何目标发起遥测请求。
- **隐私说明状态门**：隐私说明不是一句文案，而是一道前置状态门。未确认说明前一律零上报，即使默认值为开启；确认时间需持久化记录。产品不接受“安装完就开始传”的实现。
- **状态门的严格口径（产品裁定）**：未确认说明前**禁止先缓冲、确认后补发**。即：未确认期间不记录任何遥测事件到本机缓冲；确认之后才开始记录。理由：“先缓冲”意味着已经把行为写入本机文件，一旦实现细节走样或用户长期不确认，就退化成事实上的先采集后追认，无法向员工解释。若实现上确有困难，最宽松的可接受形态是“仅内存暂存、确认即写入、关闭即丢弃”，不得落盘、不得跨启动保留。
- **缓冲淘汰的产品后果（已接受）**：缓冲滚动淘汰会造成管理员侧健康数据残缺。遥测只用于产品健康和入口修复判断，不得作为员工评价或绩效依据；指标判定时必须先检查样本覆盖度（见 §16.2 与 §17）。

### 15.3.1 首次隐私说明文案要求

首次启动说明必须说清楚三件事，且不能用技术术语堆砌：
1. 上报什么：匿名设备编号、应用版本、入口成功/失败的次数与原因类别；不采集原始搜索词、完整路径、个人入口内容和 IP。
2. 为什么上报：帮助管理员发现打不开的入口和同步是否成功，不用于评价个人。
3. 如何关闭：设置中的开关位置与关闭后的影响。

### 15.3.2 实现要求

- 使用自建 `trackEvent()` 封装，不引入第三方外网 SDK。
- 事件发送失败不能阻塞入口打开；离线事件队列有数量和保留期限上限。
- 同一失败不得在轮询中重复上报形成事件风暴。
- 上报失败按离线处理，恢复后按缓冲策略重试，超出上限后丢弃最旧事件。
- 上线前由产品、架构和测试共同校验事件字典与脱敏结果。

## 16. 成功指标与 MVP 验收

### 16.1 北极星指标

**团队入口周有效使用率**：一周内至少成功执行过一次团队入口的已初始化员工设备数 / 该周已成功同步的活跃员工设备数。

MVP 试点目标：首月达到 70% 以上。该指标验证入口是否真正进入日常工作，而不是只完成安装。

### 16.2 核心量化指标

| 维度 | 指标 | MVP 目标 | 验证方式 |
|---|---|---:|---|
| 可发现性 | 新员工从打开应用到找到指定团队入口的任务完成率 | ≥ 90% | 5–8 人可用性测试，指定 3 个真实入口 |
| 可发现性 | 上述任务中位完成时间 | ≤ 30 秒 | 可用性测试 |
| 打开效率 | 从主窗口可见到执行常用入口的交互步数 | ≤ 2 步 | 任务走查 |
| 发布效率 | 管理员完成“修改一个入口并发布”的中位时间 | ≤ 2 分钟 | 管理员任务测试 |
| 更新时效 | 管理员发布到在线员工显示新版本 p95（含一个 30 秒轮询周期，不做实时推送） | ≤ 45 秒 | 试点日志 |
| 隐私合规 | 遥测出站请求出现第三方外网域名或服务端日志出现来源 IP | 0 条 | 埋点审计与日志检查 |
| 隐私可控 | 员工能找到并成功关闭遥测开关的比例 | 100% | 可用性测试 |
| 离线可用 | 有成功缓存的设备在管理员离线时展示团队页成功率 | 100% | 断网/关服务测试 |
| 性能 | 有缓存时首屏团队卡片可见 p95 | < 1.5 秒 | 性能测试 |
| 稳定性 | 员工端无崩溃会话率 | ≥ 99.5% | 匿名异常事件 |
| 正确性 | 新版本校验失败时旧缓存保留率 | 100% | 故障注入测试 |
| 支持闭环 | 在线失效反馈送达管理员成功率 | ≥ 99% | 试点日志 |
| 数据完整度 | 遥测事件因缓冲滚动淘汰导致的丢失率；上报成功的设备覆盖比例 | 丢失率 < 20%，覆盖 ≥ 70% 试点设备 | 只读诊断接口 `telemetryCompleteness`（含 `sampleJudgable`） |
| 入口健康 | 试点两周后仍被报告失效的团队入口占比（**条件判定指标**） | < 5% | 按入口聚合反馈；样本覆盖不足时改用逐项人工确认 |
| 隐私 | 抽查事件中出现原始搜索词、完整个人路径或原始硬件序列号 | 0 条 | 埋点审计 |

### 16.3 MVP Go / No-Go

满足以下条件才可扩大到完整 10–50 人团队：

- 所有 P0 验收标准通过。
- 离线缓存、版本更新、权限拒绝和损坏数据四类故障演练通过。
- 5–8 名非项目成员完成指定入口任务，完成率达到 90%。
- 没有可导致任意脚本执行、管理员口令泄露、员工回写团队配置的 P0 安全缺陷。
- 遥测审计通过：无第三方外网域名出站、服务端不记录来源 IP、脱敏字段抽检 0 例越界。
- 遥测样本可判定：诊断接口 `telemetryCompleteness.sampleJudgable = true`（事件丢失率 < 20% 且试点设备覆盖 ≥ 70%），可直接作为判定依据，无需人工二次加工；不达标时“入口健康”只作为参考，改用逐项人工确认，不作为 Go/No-Go 硬门槛。
- 反馈投递不谎报：待发送队列中的反馈显示为“待发送”，服务端确认后才显示“已送达”；超限丢弃必须可见告知，不得静默丢失。
- 试点管理员能独立完成编辑、发布、查看反馈，不依赖改文件或命令行。

## 17. 风险与假设

| 风险/假设 | 影响 | 当前判断 | 缓解与验证 |
|---|---|---|---|
| 管理员客户端是同步单点 | 新版本和反馈在管理员离线时延迟 | 高概率、已接受 | 缓存保证打开不中断；明确离线与数据时间；试点统计管理员在线窗口 |
| 内网发现、Windows 防火墙或安全软件阻断 | 新设备无法同步或反馈 | 高 | 首次连接给出可诊断状态；与架构师制定安装检查；试点覆盖常见安全策略 |
| 软件安装路径在设备间不同 | 同一 exe 入口只在部分电脑有效 | 高 | 允许快捷方式/扫描候选；错误区分本机缺失；支持重新定位和反馈 |
| 共享盘盘符、权限不一致 | 文件夹入口失效 | 高 | 尽量展示清晰目标说明；区分权限与网络不可达；管理员按反馈聚合修正 |
| 管理员口令传播 | 未授权人员可编辑团队页 | 中高 | 明显编辑状态、失败限速、短时会话、发布记录；规模扩大后重新评估身份方案 |
| Ctrl+Space 与输入法冲突 | 热键不可用或打断输入 | 高 | 首次检测并提示改键；托盘和主窗口入口始终可用 |
| 30 秒轮询产生视觉跳动 | 员工被打断 | 中 | 仅版本变化时更新；软更新保留上下文；无变化不重绘 |
| 网页“打开成功”不代表业务可用 | 自动健康判断误报/漏报 | 高 | MVP 只判断 URL 与系统交接；业务失败依赖主动反馈 |
| 卡片数量膨胀后重现信息过载 | 产品价值下降 | 中 | 单层最多 8 组、总量上限、P1 健康中心与重复检查 |
| 无账号导致反馈责任不清 | 管理员难以追问个案 | 中 | 匿名设备聚合 + 可选设备显示名；MVP 不承诺人员级追踪 |
| 员工担心使用监控 | 降低采纳与信任 | 中 | 不做排行榜；不采原始搜索词和个人内容；首次启动明确说明并提供关闭开关 |
| 遥测默认开启被误读为监控 | 员工关闭上报，导致健康度数据缺失 | 中低（已加状态门后下调） | 说明文案聚焦“发现打不开的入口与同步状态”，明确不评价个人；未确认说明前零上报；设有关闭开关并纳入试点观察 |
| 遥测样本因缓冲淘汰与设备离线而残缺 | 入口健康类指标样本不足，误判入口质量 | 中 | 遥测只作为辅助证据；试点前两周对该类指标不设硬判定；改用逐项人工确认；管理员试点期间保持工作日在线窗口 |
| `sampleJudgable` 长期为 false（架构 R21） | 有人以“指标拿不到”为由推动改用云端/第三方埋点 | 中 | 既定处置是回到 P1「管理员内容健康中心 + 逐项人工确认」，不得因此上云；推翻门槛：必须同时提出“不引入外网域名、不记录来源 IP 前提下提升样本量”的方案，并经 PM 与架构师共同评审，仅以指标缺失为由不成立 |
| 用残缺样本硬判定入口健康（架构 R22） | 管理员删改本来正常的入口 | 中高 → 已根除 | 条件判定机制：`sampleJudgable=false` 时入口健康不设硬门槛，仅作参考 |
| 团队实际规模超过 50 人 | 内嵌服务、权限和管理模型不再合适 | 中 | 先限制目标规模；达到阈值时重新评估独立服务与权限模型 |
| 当前缺少一手访谈数据 | 部分优先级和文案仍是假设 | 高 | 开发中完成 2 名管理员 + 5 名员工访谈/可用性测试，更新 Confidence |

### 关键待验证假设

1. 目标团队每天至少有 5 个跨软件/文件夹/网页的高频入口。
2. 一层分组在 200 个入口上限内足够，实际高频入口更可能小于 60 个。
3. 管理员通常有较稳定的开机时段，允许新版本延迟而不影响缓存使用。
4. 员工愿意使用独立启动器，只要首次可用不要求个人配置。
5. 结构化反馈比在群里报错能显著缩短管理员定位时间。

## 18. 试点计划

## 20. 给设计与架构协作方的产品边界

### 给设计师

- 优先支持扫视和短路径，不把主界面做成传统复杂后台。
- 两个主 Tab、单层分组、统一卡片骨架是产品结构，不应在视觉阶段改成多层目录。
- 离线、旧缓存、编辑模式、未发布草稿、失败与待发送反馈必须有可见状态。
- 功能图标统一使用 SVG 图标库，具体库由架构师锁定；不得用 emoji。
- 不使用紫色到粉色渐变；示例文案使用本文真实团队场景。

### 20.1 与架构方案已确认的边界

1. 遥测不接入第三方互联网服务，改为自建 `trackEvent()` + 本机缓冲 + 批量上报管理员客户端；默认开启但首次启动必须说明并提供关闭开关；关闭后停止记录、清空缓冲、不再请求；隐私说明未确认前零上报。
2. 8 组 / 200 入口的容量上限与发布权限均在服务端强制校验；员工端 UI 隐藏编辑入口不是安全边界。
3. 版本先后只比较服务端 revision，界面“数据时间”取服务端发布时间；MVP 不做自动提权（`runAsAdmin` 出范围）。
4. 发布到员工可见的时效口径为“最快一个 30 秒轮询周期”，p95 ≤ 45 秒；MVP 不做长连接实时推送。
5. 同步状态采用“状态 + 原因”表达（架构 v1.2 的 7 态 + `offlineReason` + `hasCache`）；状态与伴随字段只能由同步服务写入。
6. 失效反馈投递为 `PENDING` / `SENT` / `DROPPED` 三态；仅服务端确认接收才允许 `SENT`，`DROPPED` 必须可见告知。
7. 遥测完整度通过只读诊断接口 `telemetryCompleteness` 暴露，含 `sampleJudgable`，直接支撑 Go/No-Go 第 4 条判定。

### 给架构师

- 本文只定义产品结果，不锁定内部实现。
- 必须保证团队页单向同步、完整数据校验后才替换缓存、版本无变化不触发页面重绘。
- 管理员客户端退出是同步服务停止的显性事件，但员工端已缓存入口仍可用。
- 身份仍是设备标识 + 管理员口令，不引入账号体系。
- 需要给出 Windows 热键冲突、系统打开失败、共享路径权限、休眠唤醒和安全软件拦截的可诊断错误类别。
